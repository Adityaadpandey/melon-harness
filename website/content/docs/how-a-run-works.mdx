The harness around the model picks which model to use, runs the checks, and decides whether the work counts as finished. This example run is put together to show the flow. Each status line is a message zerd prints, and the last two lines are a summary rather than the exact format.

```text
> change unique_by() to take a key function and drop the seen= argument

  Routing to the strong model (read by the fast model): claude-opus-5-5
  Verifying: python3 -m pytest -q -x tests/test_unique.py
  Verification failed (python3 -m pytest ...); repair attempt 1/2
  Verifying: python3 -m pytest -q -x tests/test_unique.py
  The change breaks 1 public signature(s) (utils.py: unique_by() no longer accepts `seen`); asking to keep old calls working
  Verifying: python3 -m pytest -q -x tests/test_unique.py
  Independent review of the diff...
  Reviewer found issues; sending them back for a fix
  Independent review of the diff...

  status: verified   checks: 1 passed   review: clean   citations: 4 checked, 0 unverified
  Rounds: 9 used, 10 estimated, +10 points (within the target)
```

Code makes every decision in that run: which checks to run, whether a failure is new or was already there, whether a public signature broke, and whether the review goes again.

## The path of a request

<Mermaid chart={`flowchart LR
    A([Your request]) --> B{"Classify<br/>no model call"}
    B -->|small| F[fast model]
    B -->|ordinary| D[default model]
    B -->|hard| S[strong model]
    F & D & S --> L["Agent loop<br/>stream, run tools, repair"]
    L -->|only reads| ANS
    L -->|edits files| V{"Checks on the<br/>changed files"}
    V -->|fail, new| R1["Repair round<br/>max 2"]
    R1 --> V
    V -->|fail, already broken| NOTE["Leave it, report it,<br/>end as unverified"]
    V -->|pass| SG{"Signature<br/>guard"}
    SG -->|public API broke| R1
    SG -->|ok| RV{"Independent review<br/>if enabled or asked"}
    RV -->|findings| R2["One fix,<br/>review again"]
    R2 --> G
    RV -->|clean| G["Citation check<br/>paths and lines on disk"]
    NOTE --> G
    G --> ANS([Answer + honest status])
    L -. loop detected .-> S
    R1 -. still failing .-> S`} />

1. Classify. Rules pick a model size for the request without a model call, and say why.
2. Work. The agent loop reads, edits and runs tools.
3. Check. If files changed, checks run on those files only. New failures go back for repair, up to 2 rounds.
4. Guard. A broken public signature sends the agent back once.
5. Review. An independent review of the diff runs if you asked for it or turned on `auto_review`.
6. Cite. Every file and line in the answer is looked up on disk.

## The five endings

Every run ends in exactly one of these states.

| Status | Meaning |
|---|---|
| `verified` | Files changed and the checks passed. |
| `unverified` | No checks exist for this change, or a check was already failing before the run. |
| `verification_failed` | Checks still fail after the repair rounds. |
| `failed` | An API error, a loop, or the deadline. |
| `done_no_changes` | Nothing was edited, for example you asked a question. |

Each request is a task with a fixed lifecycle. The code checks every transition, so a run can't jump from `failed` to `verified`, and every transition is written to a trace you can read later.

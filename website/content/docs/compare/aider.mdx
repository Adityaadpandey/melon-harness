Aider is a widely used open-source AI pair programmer for the terminal, built around chatting and committing to git. zerd shares the terminal and the any-model approach. The difference is what happens after an edit, and how long a task can run without you.

Details about Aider on this page are limited to its well-known design. For its exact current options, see Aider's own docs.

## At a glance

| | zerd | Aider |
|---|---|---|
| Models | [15 built-in providers](/docs/models) including Claude, GPT, DeepSeek, Gemini, Groq, Ollama and LM Studio, plus a Codex login and any OpenAI or Anthropic format server | Many providers, local models included |
| Provider fails | Fails over to the next provider in the chain and tells you | You switch models |
| After an edit | Picks checks for only the changed files (tests that import the module, `cargo check`, `go vet`, `eslint`, your own `verify_commands`) and runs them | Runs lint and test commands you configure |
| A check fails | Tells apart "the agent broke it" from "it was already failing" by re-running on the pre-run files | Output goes back to the model |
| Review | A second model reviews the real diff, a verifier refutes weak findings, a repro agent tries to trigger HIGH ones | None built in |
| Paths in the answer | Every `path` and `path:line` is checked on disk | Not checked |
| Finding code | BM25 `search`, `outline`, one-symbol reads, and a live tree-sitter symbol graph for 9 languages | Repo map |
| Undo | `/undo` from `refs/zerd/backup`, no stash and no index change | Each change is a git commit |
| Long tasks | Sub-agents, parallel workers in separate git worktrees, resumable sessions | Chat-driven |
| Memory | Learns rules from your corrections into your own `AGENTS.md`, capped at 30 per repo | Conventions file you maintain |
| Written in | Rust, one binary, no Python or Node | Python |
| Source | Source-available, free to run | Open source |

## What zerd adds

**Checks that are chosen for you.** After edits zerd looks at what changed and picks the checks, never a whole build. `pytest` runs only the tests that import the changed module, found through an import graph. The details are on the [Verification](/docs/verification) page.

**A reviewer that has to prove it.** Say "review my changes", "review my last 3 commits" or "review PR #42". Reviewers read the diff through lenses (behavior, approach, failures, project rules, git history, security, and a producer-to-consumer contracts reviewer). Every finding then goes to a verifier whose default is to refute it. See [Reviews and fixes](/docs/reviews).

**Edit-time diagnostics.** Each edit comes back with only the problems that edit introduced: Python syntax and `ruff`, JSON and TOML parsing, `node --check`, `gofmt`, and for TypeScript your project's own `tsserver`, kept running.

**It will not edit what it has not read.** Editing a file the agent has not read this session, or that changed on disk since, is refused. If you edit a file in your editor mid-run, the agent is told and re-reads rather than overwriting you.

**Cheap context.** `read_file` returns only new lines or a diff when a file changed. Big tool output is archived with an id the model can recall. In a real 21-call session 85% of input came from cache.

## How zerd works differently

**It knows whose failure it is.** When a check fails, zerd swaps in the pre-run copy of your files, runs the same check again, and puts the agent's files back. An error that was already there is reported as "was already failing before your change; leaving it alone", and the run ends `unverified`. Failures the agent caused go back as a repair request, up to 2 rounds, then to the strong model.

**The author never grades its own work.** A different model reviews the real diff in a fresh context with read-only tools. A verifier tries to refute each finding, six at a time, naming the exact line it read. A confirmed HIGH goes to a repro agent in a sandboxed copy; if it cannot make the defect happen, the finding is capped at MEDIUM.

**It will not invent files.** Every `path` and `path:line` in the final answer is looked up in the real tree. An invented file or a line past the end of one goes back for one correction.

**Every run ends in an honest status:** `verified`, `unverified`, `verification_failed`, `failed` or `done_no_changes`. Never a bare "done".

## What the benchmarks do and do not show

zerd has been benchmarked head to head against Claude Code only, in two rounds. There is no head-to-head against Aider, so nothing below is a claim about it. What the rounds do show is how zerd's approach behaves:

| | zerd |
|---|---|
| 11 tasks, one run each | 10 / 11 passed, the miss became the [signature guard](/docs/verification) |
| Input served from cache | 87% (85% in a real 21-call session) |
| Webhook reliability test, 15 scenarios | 15 / 15 with an automated test, 12 real bugs found against real PostgreSQL, real Redis and a real SIGKILL |

One project, one run each, and the agents did not test at the same depth. Details and caveats are on the [Benchmarks](/docs/benchmarks) page.

## Where Aider is ahead

- **It is open source.** zerd is source-available: you can read and run it, not copy or modify it. See the [license](/docs/license).
- **A git-first loop.** Every Aider change is its own commit, which many people prefer for review and rollback. zerd leaves your git state alone and uses its own backup ref.
- **Maturity and community.** Aider has been around longer and has a large user base.
- zerd has no IDE extension or image input yet.

## Which should you use

Choose Aider if you want an open-source tool and a tight chat-and-commit loop. Choose zerd if you want the agent to choose and run checks, review its own diff, and report which claims were verified, so you read a short receipt instead of the whole change.

Try zerd on one small change with the [quickstart](/docs/quickstart). `/undo` puts everything back.
